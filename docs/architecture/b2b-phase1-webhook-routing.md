# B2B phase 1 — tenant-bound webhook routing (draft)

This is the first hardening slice, not external partner certification. The existing Funded event envelope and HMAC remain unchanged. Only operator-configured tenant IDs can send events. Partner aggregate IDs use the platform account externalRef, not Funded-specific metadata. There is one operator-managed destination per tenant, with bounded parallel tenant queues.

## Deployment gate (do not merge before completing)
- Verify the immutable ACG Funded tenant ID against the authoritative MongoDB tenant, service credentials, existing outbox and Funded account mapping. Set ACG_FUNDED_WEBHOOK_TENANT_ID in staging and coordinate production config with deployment. Missing/invalid binding intentionally prevents an enabled relay from starting. Never infer tenant from metadata.
- PARTNER_WEBHOOK_ROUTES_JSON is optional, an operator secret JSON array of {tenantId,url,secret}; maximum 15 additional tenants. Validate active tenant ownership, endpoint control, DNS/egress safety and distinct signing secrets outside the app before configuring. Do not expose this mechanism to partner users. HTTPS required; redirects rejected.
- Create/verify the compound tenant outbox index; inspect pending/dead events by tenant and reconcile pre-existing backlog. Never reassign a route to a different business or silently discard unmatched records.
- Run full CI and isolated staging with Funded and a synthetic partner: verify provisioning, native and federated sessions, signed snapshot, deal and control events, timeout isolation, retry, restart, reconciliation and zero cross-tenant delivery. Keep production single writer; multi-replica claims/fencing are not implemented.
- Confirm production rollout and rollback with no Funded event loss; legacy revision must never run with external tenants enabled.
- Remaining: self-service subscriptions, per-destination delivery records and replay, secret rotation, quotas, validated egress/SSRF controls, tenant audit, fine-grained API scopes, business auth and policy generalisation. Unknown/unconfigured tenants intentionally do not enqueue partner events; do not provision an integration before its route and acceptance are ready.

## Incremental read-only scopes
Partner integration credentials can be issued with accounts:read, ledger:read and trades:read independently. Existing accounts:write credentials keep their previous permissions during migration. Sensitive admin observability and operations endpoints are deliberately excluded from the new read-only access. This is additive least privilege, not complete mutation-scope segmentation; do not issue broad legacy keys to new partners before that review. Test tenant boundaries in actual MongoDB and HTTP/WS acceptance before onboarding.

## Phase 1 expanded acceptance
The API now has explicit middleware on each route. New partner keys should use accounts:provision, accounts:read, accounts:control, accounts:observe, risk:write, risk:read, risk:control, ledger:read, ledger:write, credentials:write, grants:write, federation:write, trades:read, reports:read and reports:reconcile only as needed. Existing accounts:write retains legacy permissions; do not issue it to external partners. Funded policy migration and platform-wide health/recovery remain legacy operations, not generic partner entitlements. Provisioning and challenge policy modification are privileged; business admins are not trader principals.
The two-tenant CI test uses a dedicated disposable Mongo replica set, real service credentials, real account provisioning and transactions, native and federated sessions, actual HTTP/WS, and a controlled webhook transport double. It is not a production database or external network acceptance test. Production backup restoration and authoritative tenant binding are still separate gates.

## Operator-managed partner subscriptions and replay
Partner routes accept optional eventTypes (ACCOUNT_SNAPSHOT, DEAL_CREATED, ACCOUNT_CONTROLLED) and keyId. Filtering applies to new events only; previously queued immutable facts continue delivery. For key rotation coordinate receiver acceptance of both old/new keys, change the tenant route secret/keyId, deploy, verify signed deliveries and retire the old receiver key. No key is stored in Mongo or exposed to the client. One approved endpoint per tenant; self-service endpoint editing and multi-destination fanout are deferred to the business control plane. Partner-only deployments no longer require Funded credentials. New external routes require public DNS HTTPS on port 443; public IPv4 is resolved on each attempt, private/special addresses are rejected, the selected IP is pinned while TLS authenticates the hostname, and redirects are not followed. This is an intentionally restrictive first release; the legacy Funded path retains its prior HTTP transport. Independently verify endpoint ownership and network egress in staging before opening a route. No external partner endpoint is enabled by this PR.
Operator replay requires REPLAY_PLATFORM_TENANT_ID, REPLAY_PLATFORM_EVENT_IDS and explicit REPLAY_PLATFORM_APPLY=true to mutate; default is dry run. Only dead immutable facts for the selected active, configured tenant are replayed atomically. Preserve event IDs and receiver deduplication. Unmatched records remain quarantined; do not delete or reassign them. Existing legacy script invocation now requires tenant and apply confirmation.
