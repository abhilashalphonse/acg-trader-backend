## Purchase lifecycle
- Synthetic, versioned fixture catalog only: USD 5, 10 and 25; amounts are integer cents and one cent equals 10^10 pico-USD. No approved sale denominations, discounts, currency conversion, taxes or commercial markup. Client supplies SKU and UUID idempotency key, not amounts. Owner-scoped order creation/status require current authorization. Purchase owner is tenant/user rather than trading account; no trading balance changes.
- Synthetic verifier authenticates bounded raw canonical JSON bytes and timestamp with a dedicated injected 32-byte HMAC key and constant-time comparison, rejects stale (>5 minutes), malformed/extra fields and signature mismatch. Separate webhook authorization required. This is NOT a real processor signature protocol. Provider event contains order ID, globally unique event ID, payment ID, event type, USD and amount. No user identity from webhook; stored purchase determines owner. Raw body, signature and key not persisted.
- Event, order transition, wallet and journal writes in one majority snapshot transaction, wallet/order CAS, globally unique provider event and payment identifiers, owner/idempotency unique order key. Identical event replay returns current status plus original result; changed payload using same event ID or payment reused across orders fails. Concurrent duplicate-key conflict is safely retryable with same signed event; unknown commit reconciled by status/event replay, never a second payment.
- Exact CAPTURED on CREATED grants fixed credits once. Mismatched capture is sticky review, no credit mint. Duplicate capture does not grant more. Full reversal before capture prevents late mint. Partial or contradictory reversal before capture stays in review; no auto credit. Refund/chargeback events describe cumulative confirmed reversed amount, not deltas, so duplicate types never double reverse.
- Full confirmed reversal of a credited purchase atomically reduces available and net credited, increases reversed lifetime total; if available insufficient, retain restriction and hold for reconciliation, never negative balance, never seize reserved credits or erase spent credits. Partial/ambiguous evidence restricts wallet, no automatic partial debit. Contradictory amounts require sticky operator review, even if later matching event arrives. New managed reservations and not-yet-claimed dispatches blocked while pending reversal count >0, existing attempted work may settle and undispatched reservations may release. New order creation checks restriction but no external payment possible; existing orders may be credited if exact signed capture arrives. A previously confirmed full reversal may be reconciled after enough available credit returns; atomic clearing of restriction only when reversal fully applied. No automatic retries, refunds, write-offs, debt collection, or arbitrary operator balance adjustment. No actual merchant refunds initiated. BYO inference unaffected.
- Balance invariant net credited = available + reserved + spent; reversed is separate cumulative counter. Event journal includes reversal state. Existing synthetic fixture funding is isolated only. Payment records are append-only at application layer, not tamper-proof against DB administrators.
- Integrated replica-set acceptance exercises signed and stale/tampered events, duplicate order/event/payment identity, concurrent capture, cross-owner isolation, late capture after reversal, mismatched amounts, partial refund, full refund, spent credit and held reservation reversal, restricted dispatch/reserve, idempotent reconciliation, atomic rollback and journal invariants. Disabled-route smoke includes credit/payment endpoints. Production mounts absent.
